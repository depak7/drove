Describe a feature. Approve one plan. Come back to a reviewed branch.

Drove runs a disciplined build–review–verify cycle on your own machine, using the coding CLIs you already have installed and logged in. No API keys. No cloud service. No second subscription.

The model that wrote it never grades its own homework

That is the whole idea. A reviewer which has read the implementer's reasoning tends to ratify it — so the reviewer runs in a fresh session every round and sees only what a human reviewer sees: the diff, and the stated intent. Claude writes, Codex judges. Or the other way round. You choose per stage.

Nothing runs in your checkout

Every feature gets its own git worktree per repository. Runs never collide, and your working copy is never touched. A worktree is removed only once its commits are in the base branch — unmerged work is preserved and the recovery command printed.

One change, several repositories

A workspace is a named set of repos worked on together, so one feature can rename an interface in your API and fix every caller in your web app, on a branch that shares a name in both.

Evidence, not a green tick

Every run writes a pack: what was asked, what changed, the reviewer's verdict each round, your test output, cost, and the command to reopen any agent session. If one model both wrote and reviewed, it says so.

Your hands stay on the wheel

Read the diff file by file, browse the whole worktree, or open a real shell inside it and run the tests yourself. Stop a run mid-flight; resume it later from where it stopped.

Best at the work you keep postponing

Well-specified but tedious — where you already know what “done” looks like, and the cost is the hour of typing rather than the thinking.

Cross-repo renames

One workspace, two worktrees, one branch name in both.

rename greeting() in api and update every caller in web

The tests you never wrote

A second model reviews them, so it will not wave through tests that assert nothing.

the payment module has no tests for refunds

Migrations you keep deferring

Your own build and test commands gate delivery.

upgrade to pydantic v2 and fix what breaks

Bugs from a stack trace

Paste the trace. The plan comes back naming real files.

this fires when the session cookie expires

The frontend break tests cannot see

Optional browser checks open the page after a run and screenshot it — a component that throws on render is caught even though the build passed.

Several at once

The approval gate is a state, not a prompt. Queue five in the morning, approve the plans over coffee, come back to five reviewed branches.

Two commands

Run it from anywhere — Drove is one machine-wide daemon, not a per-project tool. Repositories are pointed at, not run from. 

# needs claude, codex or opencode already installed and logged in
uv tool install git+https://github.com/depak7/drove
drove serve   → http://localhost:8787

What it does not do

Stated here rather than discovered later.

  • It cannot decide what to build. You approve the plan; if you cannot tell whether the plan is right, nothing downstream saves you.
  • Cross-repo branches do not merge atomically. They share a name and must be merged together — the evidence pack says so, but nothing can enforce it.
  • After two failed review rounds it stops and asks you, rather than asking a third model to break the tie. That stage is designed, not built.
  • The macOS app is unsigned today, so it installs from source rather than a download.
  • It spends real tokens on your own subscriptions. Every run records what it cost.
